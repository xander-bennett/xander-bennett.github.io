[01]retrieve38 ms

Find the right tables before writing a line of SQL.

Retrieval runs over the dbt manifest and catalog rather than the raw schema, so the agent sees model descriptions, column docs, tests, accepted values, and lineage. The five best matches are all it is allowed to use.

In plain terms: the assistant looks up which tables are relevant and is forbidden from using any others. Most wrong answers from AI over data start with a guessed table or column; this removes the guess.

[02]draft1.3 s · 312 tokens

Write SQL that can only name what it found.

The model gets the question and the five retrieved model docs, and returns one SELECT as JSON. The first attempt below is what it actually wrote: it reached for a dim_level table that exists in its head but was never retrieved.

In plain terms: the assistant writes the query, and its first try contains a plausible mistake. The next stage is where that mistake gets caught, which is the whole point.

-- attempt 1 · constrained to the five retrieved modelsselect  e.job_family,  count(*) as below_midpointfrom fct_band_position as bjoin dim_employee as e on e.employee_id = b.employee_idjoin dim_level as l on l.level_id = e.level_idwhere e.is_active  and l.level_name = 'L4'  and b.compa_ratio < 1.0group by 1order by below_midpoint desc;
Confident and wrong in one place. The join to dim_level is the kind of guess text-to-SQL systems make constantly. Here it cannot survive, because the next stage checks every referenced table against the retrieved set.
[03]validate · repair4 checks · 1 repair · 0.6 s

Four checks before anything runs. One fails, one repair.

Parse as DuckDB SQL, confirm a single read-only SELECT, confirm every referenced table is in the retrieved set, dry-run with EXPLAIN. A failure goes back to the model with the exact error, up to three times. Attempt 1 failed the grounding check; attempt 2 passed all four.

In plain terms: before the query touches any data, it has to pass four tests. The mistake from the previous step is caught here, the assistant is told exactly what was wrong, and it fixes it. Nothing unverified ever runs.

[04]execute3 rows · 12 ms

Run it read-only, capped, and timed.

The validated query runs on a read-only DuckDB connection with a 200-row cap. Latency and token cost are logged on every run, so a change that improves accuracy by adding two model calls shows its price.

In plain terms: the query runs against a copy of the data it cannot change, with a limit on how much it can pull back, and the cost and speed of every answer are recorded.

[06]proveoutside the loop · grades every lap

Then prove it, on every change.

A golden set of questions with reference queries, an eval that compares result sets by value, and a CI gate that fails a pull request when accuracy or retrieval recall drops more than three points below the committed baseline. The targets are written down first so the numbers can miss them in public.

In plain terms: the assistant is re-tested every time its code changes, against questions with known correct answers. If it gets worse, the change cannot ship. This is the part most AI features skip.

[07]what i build

Three things companies pay for, in plain terms.

Each one ships with a test that says whether it is working. One is the loop above, in progress. Two are queued behind it, and appear on GitHub once they have code.

Ask a question, get a trustworthy answer

An assistant that turns a plain-English question like “which teams are paid below market?” into a query against the company's data, checks its own work, and shows where the numbers came from.

For a company, this means fewer wrong numbers reaching a CFO, and analysts spending their time on judgment rather than lookups. grounded-sql-agent · in progress

Turn messy spreadsheets into clean records

Customer files rarely match the format the software expects. This maps the incoming columns onto a standard set, flags uncertain matches for a person to check, and learns from the corrections.

For a company, this means onboarding a new customer in days rather than weeks, with less manual cleanup each time. schema-mapper · queued

Catch AI mistakes before customers do

A safety net that re-tests an AI feature every time it changes, compares the results with the previous version, and blocks the release if quality drops.

For a company, this means AI changes ship with evidence behind them, and problems are found in a test run before a customer sees them. regression-gate · queued

[08]background

Six years in data, then AI.

I came to AI engineering from the data side. In that work, a wrong answer is a number a finance leader has already repeated in a meeting, and that is the standard I hold AI systems to. It is why the loop above spends more of its time checking than generating.

I spent six years at Addepar, a wealth-management data platform, going from operations analyst to owning the reporting and data-modeling layer. I then led an analytics rebuild at Dorsia, including a cloud migration, and ran a small team.

Today I'm a Customer Success Engineer at Pave, a compensation platform. I run technical implementations, clean up the HR and pay data that makes customers' software work, and build the AI workflows my team runs every week: a comp-cycle forecasting agent (Cycle Radar), scheduled CRM and reporting updates, and a customer-feedback sweep that drafts product requests from calls and email.

Outside work: two kids, tabletop games, and a side project teaching game development.
